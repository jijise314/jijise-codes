# 순차 탐색 · BST · AVL 트리 성능 비교

| 파일 | 설명 |
|---|---|
| `AvlTree.h` | 자료형과 함수 선언 |
| `AvlTree.c` | 배열·BST·AVL 트리 구현 |
| `main.c` | 난수 생성, 삽입·탐색, 결과 출력 |
| `result.txt` | 분석에 사용한 실행 결과 |

숫자 비교 횟수는 새 값(또는 탐색 키)과 저장된 값을 비교한 횟수이며, 트리는 노드 하나를 방문할 때 1회로 계산했습니다.
AVL의 높이 계산과 회전 판단은 포함하지 않았습니다.

## 실행 결과

**저장된 서로 다른 값 : 97개** (100개 중 중복 3개 제외)

| | 배열 | BST | AVL 트리 |
|---|---|---|---|
| 생성 비교 횟수 | 4,794 | 713 | 535 |
| 길이 / 높이 | 97 | 14 | 8 |
| 탐색 총 비교 횟수 | 4,515 | 426 | 330 |
| 탐색 평균 비교 횟수 | 90.30 | 8.52 | 6.60 |

탐색 키 50개 중 5개는 성공, 45개는 실패했습니다.

## 분석

**BST와 AVL 트리의 높이가 다른 이유**
두 트리에는 같은 값이 같은 순서로 들어갔습니다.
하지만 BST는 삽입 순서대로 모양이 굳어져서 한쪽 경로가 길게 자랐고, 높이가 14가 되었습니다.
AVL 트리는 삽입할 때마다 좌우 높이 차이를 검사하고 회전(이번 실행에서 46회)으로 균형을 맞췄습니다.
그 결과 높이가 8로, 97개 노드의 이론적 최소 높이 7에 가깝게 유지되었습니다.

**트리의 높이가 탐색에 미치는 영향**
트리 탐색의 비교 횟수는 루트부터 내려간 노드 수이므로, 높이가 곧 최악의 비교 횟수입니다.
BST에서는 깊은 경로에 걸린 키(677, 650)가 14번 비교했지만, AVL 트리에서는 모든 키가 7번 이하로 끝났습니다.
반대로 작은 값(24, 26 등)은 BST의 얕은 쪽에 있어서 3번 만에 끝나기도 했습니다.
정리하면 BST는 키에 따라 3~14번으로 편차가 컸고, AVL 트리는 5~7번으로 고르게 낮았습니다.

**생성 비용 비교**
배열은 새 값마다 저장된 값을 처음부터 끝까지 확인해야 하므로 비교 횟수가 데이터 수의 제곱에 비례해 늘어납니다(4,794회).
트리는 경로 하나만 내려가므로 훨씬 적었습니다.
AVL 트리는 높이가 낮아 BST보다도 비교가 적었지만(535 vs 713), 회전과 높이 갱신이라는 추가 작업이 있다는 점은 고려해야 합니다.

**탐색 비용 비교**
순차 탐색은 실패할 때마다 97개를 모두 확인해서 평균 90.30회가 걸렸습니다.
BST는 비교 한 번에 탐색 범위를 크게 줄여 평균 8.52회로 줄었습니다.
AVL 트리는 탐색 방법이 BST와 똑같은데도 평균 6.60회로 가장 적었습니다.
이 차이는 전적으로 트리 높이(14 vs 8)에서 나옵니다.

## 결론

배열은 구현이 가장 간단하지만 생성과 탐색 모두 가장 느렸습니다.
BST는 배열보다 훨씬 빨랐지만, 삽입 순서에 따라 트리가 기울어 성능이 들쭉날쭉했습니다.
AVL 트리는 균형을 유지해 생성과 탐색 모두 가장 적고 안정적인 비교 횟수를 보였습니다.
결국 같은 탐색 방법이라도 **트리의 높이를 낮게 유지하는 것이 탐색 성능을 좌우합니다.**
