# 정렬 알고리즘의 성능 및 안정성 비교

선택 정렬, 버블 정렬(일반 / 조기 종료), 삽입 정렬(`>` / `>=`)을 C 언어로 구현하고,
**키 비교 횟수**, **데이터 이동 횟수**, **정렬 결과의 정확성**, **안정성(Stability)** 을 측정·검증한 프로그램입니다.

| `sorting.h` | 실험 설정 매크로, 공통 자료형(`Data`, `Counter`, `Algorithm`, `RunResult`), 모든 함수 선언 |

## 2. 구현 개요

### 2.1 데이터 구조

```c
typedef struct {
    int key1;   /* 정렬 기준 키 (0 ~ 1,000,000)             */
    int key2;   /* 정렬 기준이 아닌 두 번째 키 (0 ~ 1,000,000) */
    int order;  /* 원래 입력 순서 (안정성 검증용, 정렬 기준 아님) */
} Data;
```

- 정렬은 `key1`만 비교합니다. `key2`와 `order`는 비교하지 않으며, 구조체 전체가 하나의 데이터로 함께 이동합니다.
- `order`는 정렬 직전 입력 배열에서의 위치(0, 1, 2, …)로, 안정성 검증에만 사용합니다.

### 2.2 난수 생성

MSVC의 `rand()`는 `RAND_MAX`가 32,767이라 0 ~ 1,000,000 범위를 고르게 만들 수 없습니다.
그래서 **xorshift32** 난수 생성기를 직접 구현해 사용했습니다. 두 키는 각각 독립적으로 생성되며 중복 값도 허용됩니다.

### 2.3 비교 횟수 / 이동 횟수 측정 기준

| 항목 | 포함하는 것 | 포함하지 않는 것 |
|---|---|---|
| 비교 횟수 | 두 데이터의 `key1` 비교 1회 = 1 (결과와 무관하게 모두 기록) | 반복문 인덱스·종료 조건 비교, `min != i` 같은 인덱스 비교 |
| 이동 횟수 | 데이터 전체(구조체)를 다른 위치나 임시 변수에 복사·대입 1회 = 1 | 인덱스 변경, 원본 배열 복사, 시험 데이터 생성·사전 정렬 |

- **교환(swap)**: `temp = a; a = b; b = temp;` → 이동 3회
- **삽입 정렬**: `current = a[i]`(1회) + 한 칸씩 밀기 `a[j+1] = a[j]`(밀 때마다 1회) + 최종 대입 `a[j+1] = current`(1회)
  - 이동이 없더라도 임시 변수 저장과 최종 대입은 실제로 수행되므로 매번 2회가 계산됩니다.

### 2.4 정렬 결과의 정확성 확인

정렬이 끝날 때마다 다음 두 가지를 검사합니다.

1. **오름차순 검사**: 모든 `i`에 대해 `a[i-1].key1 <= a[i].key1` 인지 확인
2. **원본 보존 검사**: 정렬 결과의 각 데이터가 가진 `order`로 원본을 찾아 `key1`, `key2`가 같은지, `order`가 중복·누락 없이 한 번씩 나타나는지 확인
   → 두 키가 분리되지 않고 함께 이동했는지, 데이터가 사라지거나 복제되지 않았는지 검증

두 조건을 모두 만족해야 `정렬 성공 : 100 / 100` / `정렬 결과 : 성공`으로 출력됩니다.

## 3. 무작위 데이터 100회 반복 실험

매 반복마다 새 데이터 10,000개를 생성하고, **같은 원본의 복사본**을 네 정렬에 각각 제공했습니다.

| 정렬 | 총 비교 횟수 | 평균 비교 횟수 | 평균 이동 횟수 | 정확성 |
|---|---:|---:|---:|---|
| 선택 정렬 | 4,999,500,000 | 49,995,000.0 | 29,970.2 | 100 / 100 |
| 버블 정렬 | 4,999,500,000 | 49,995,000.0 | 75,053,114.8 | 100 / 100 |
| 버블 정렬 (조기 종료) | 4,998,558,070 | 49,985,580.7 | 75,053,114.8 | 100 / 100 |
| 삽입 정렬 | 2,502,769,533 | 25,027,695.3 | 25,037,702.9 | 100 / 100 |

**분석**

- **선택 정렬**: 비교 횟수가 입력과 무관하게 항상 n(n−1)/2 = 49,995,000회입니다. 최솟값을 찾기 위해 남은 구간을 끝까지 훑어야 하기 때문입니다. 반면 교환은 패스당 최대 1번이라 이동 횟수가 약 3n(≈ 30,000)으로 압도적으로 적습니다.
- **버블 정렬**: 비교 횟수는 선택 정렬과 같지만, 인접 교환으로만 원소를 옮기므로 교환 횟수가 **역순 쌍(inversion)의 수**와 같습니다. 무작위 데이터의 기대 역순 쌍 수는 n(n−1)/4 ≈ 2,500만이므로 이동은 그 3배인 약 7,500만 회로, 네 정렬 중 가장 많습니다.
- **삽입 정렬**: 삽입할 위치를 찾으면 바로 멈추므로 평균적으로 버블 정렬의 절반 정도만 비교합니다(≈ n²/4). 한 칸 밀기가 역순 쌍 하나를 없애므로 이동 횟수 ≈ 역순 쌍 수 + 2(n−1)입니다. 교환(3회) 대신 밀기(1회)를 쓰기 때문에 같은 역순 쌍을 처리해도 버블 정렬보다 이동이 약 1/3입니다.

## 4. 입력 데이터의 정렬 상태에 따른 성능 비교

### 4.1 입력 데이터 생성 방법

네 가지 입력은 모두 데이터 10,000개이며, 정렬·역순·부분 정렬 데이터는 **하나의 무작위 원본**에서 만들었습니다.
입력을 준비하는 과정(사전 정렬, 뒤집기, 교란)은 비교·이동 횟수에 포함하지 않았습니다.
각 입력을 만든 뒤 `order`를 0부터 다시 매겨, 정렬 알고리즘이 받는 입력을 "원래 순서"로 삼았습니다.

| 입력 상태 | 생성 방법 |
|---|---|
| 무작위 | 4장의 100회 반복 실험 결과 사용 |
| 이미 정렬됨 | 무작위 원본을 `key1` 오름차순으로 사전 정렬 (준비용으로만 `qsort` 사용) |
| 역순 정렬 | 정렬된 데이터를 뒤집어 `key1` 내림차순으로 만듦 |
| 부분 정렬 | 정렬된 데이터에서 **무작위 두 위치를 교환하는 작업을 250회** 수행 |

**부분 정렬 데이터의 설계 기준**

- 교환 1회는 최대 2개 원소의 위치를 바꾸므로, 250회 교환은 전체의 최대 5%(500개) 원소를 교란합니다 (`PARTIAL_SWAP_PERCENT = 5`).
- 교환할 두 위치는 배열 전체에서 균등하게 무작위로 고르므로, 가까운 위치끼리뿐 아니라 멀리 떨어진 위치끼리도 교환됩니다.
- 실제로 측정한 정렬 정도는 다음과 같습니다 (프로그램이 함께 출력).
  - **95.1%** (9,513 / 10,000개)의 원소가 정렬 후의 올바른 위치에 그대로 있음
  - 인접한 두 원소 쌍 중 **95.27%** 가 이미 오름차순
  - 삽입 정렬의 밀기 횟수로 계산한 역순 쌍의 수: 약 163만 개 (무작위 데이터 약 2,500만 개의 약 6.5%)

### 4.3 분석

**선택 정렬 – 비교는 입력과 무관, 이동은 매우 적음**

- 비교 횟수는 네 입력 모두 정확히 49,995,000회입니다. 입력이 이미 정렬되어 있어도 최솟값을 확인하려면 남은 구간을 전부 비교해야 합니다.
- 이동 횟수는 "제자리에 있지 않은 원소의 교환"에만 비례합니다.
  - 정렬됨: 교환이 필요 없음 → 0회
  - 역순: 한 번의 교환으로 양 끝 두 원소가 함께 제자리를 찾으므로 약 n/2번 교환 → 15,090회 (= 5,030회 교환 × 3)
  - 부분 정렬: 교란한 250쌍을 정확히 되돌리는 250번 교환 → 750회

**버블 정렬 – 이동 = 3 × 역순 쌍 수**

- 일반 버블 정렬의 비교 횟수는 항상 49,995,000회로 일정합니다.
- 이동 횟수는 입력의 역순 쌍 수에 정비례하여, 역순 데이터에서 최악(약 1.5억 회)이 됩니다.
- 조기 종료는 이미 정렬된 데이터에서만 극적인 효과가 있습니다 (5장 참고).

**삽입 정렬 – 입력 상태에 가장 민감**

- **이미 정렬됨**: 원소마다 바로 앞 원소와 1번만 비교하고 멈추므로 비교 9,999회. 이동 19,998회는 각 원소의 임시 저장 1회 + 최종 대입 1회입니다.
- **역순**: 각 원소가 앞의 모든 원소를 지나야 하므로 최악. 비교·이동 모두 약 n²/2입니다.
- **부분 정렬**: 비교 164만 회로, 무작위 데이터보다 약 15배, 선택·버블 정렬보다 약 30배 적습니다. 역순 쌍이 적으면 그만큼 빨리 끝나는 **적응형(adaptive)** 정렬이기 때문입니다.

**역순 데이터에서 삽입 정렬의 비교가 49,994,999회인 이유**

이론상 최악은 n(n−1)/2 = 49,995,000회이지만, 무작위 원본에는 `key1`이 같은 데이터가 약 50쌍 있습니다.
Case A(`>`)는 같은 키를 만나면 멈추므로, 일부 원소가 배열 맨 앞(j = −1)까지 가지 않고 같은 키 바로 뒤에서 멈춥니다.
(비교 횟수 차이가 1로 작은 이유는, 맨 앞까지 간 경우에는 마지막 비교가 `j >= 0` 검사로 생략되고, 같은 키에서 멈춘 경우에는 그 멈춤 비교가 추가되기 때문입니다.) 같은 이유로 버블 정렬의 역순 이동도 3 × n(n−1)/2보다 약간 적습니다.

**종합 정리**

| 입력 상태 | 비교가 가장 적은 정렬 | 이동이 가장 적은 정렬 |
|---|---|---|
| 무작위 | 삽입 정렬 | 선택 정렬 |
| 이미 정렬됨 | 삽입 정렬 = 조기 종료 버블 정렬 | 선택·버블 정렬 (0회) |
| 역순 정렬 | 비슷함 (모두 ≈ 5,000만) | 선택 정렬 |
| 부분 정렬 | 삽입 정렬 | 선택 정렬 |

- 비교가 비싼 경우(또는 데이터가 거의 정렬된 경우)에는 **삽입 정렬**이 유리합니다.
- 데이터 이동이 비싼 경우(예: 큰 구조체)에는 **선택 정렬**이 유리합니다.
- **버블 정렬**은 비교와 이동이 모두 많아 어떤 입력에서도 가장 불리하며, 조기 종료가 있어도 이미 정렬된 경우에만 이득이 큽니다.

## 5. 정렬 알고리즘의 안정성 검증

### 5.1 검증 방법

1. 정렬하기 직전에 각 데이터에 **원래 입력 순서 `order`(0, 1, 2, …)** 를 저장합니다. `order`는 정렬 기준이 아니며, 데이터와 함께 이동만 합니다.
2. 정렬이 끝나면 `key1`이 같은 데이터는 연속해서 모여 있습니다. 따라서 결과 배열의 **인접한 두 데이터**를 검사합니다.
   - `a[i-1].key1 == a[i].key1` 인데 `a[i-1].order > a[i].order` 이면 → 같은 키의 순서가 뒤집힌 것 = **안정성 위반 1건**
3. 위반이 0건이면 **안정**, 1건 이상이면 **불안정** 으로 판정합니다.
   (같은 키 그룹 안에서 모든 인접 쌍의 `order`가 증가하면, 그룹 전체의 순서가 유지된 것입니다.)
4. 이와 별도로 `key2`도 함께 출력하여, 같은 키 데이터의 순서를 눈으로도 확인할 수 있게 했습니다.

### 5.2 검증에 사용한 입력 데이터

| 시험 | 데이터 | 목적 |
|---|---|---|
| Test 1 | 과제 예시 4개: (527, 100), (527, 200), (125, 300), (892, 400) | 동작을 눈으로 따라갈 수 있는 최소 예시 |
| Test 2 | 8개: Key1 = 3, 1, 3, 2, 1, 3, 2, 1 (Key2 = 1 ~ 8) | 같은 키가 3개씩 흩어져 있는 경우 |
| Test 3 | 10,000개, **Key1 = 0 ~ 99** 무작위, Key2 = 0 ~ 1,000,000 무작위 | 키당 평균 100개 중복 → 대량 검증 |
| 보조 | 4장의 무작위 데이터 100회 (시행당 같은 키 쌍 평균 50.2개) | 실제 실험 데이터에서도 확인 |

무작위 데이터(0 ~ 1,000,000)에서는 같은 `key1`이 시행당 약 50쌍밖에 없어서 검증이 부족할 수 있으므로,
Test 3처럼 키 범위를 0 ~ 99로 좁혀 **9,900개의 같은 키 인접 쌍**이 생기도록 했습니다.

### 5.3 검증 결과 요약

| 정렬 | Test 1 | Test 2 위반 | Test 3 위반 (9,900쌍 중) | 무작위 100회 중 불안정 시행 | 판정 |
|---|---|---:|---:|---:|---|
| 선택 정렬 | 순서 바뀜 | 1 | 3,207 | 100 / 100 | **불안정** |
| 버블 정렬 | 순서 유지 | 0 | 0 | 0 / 100 | **안정** |
| 버블 정렬 (조기 종료) | 순서 유지 | 0 | 0 | 0 / 100 | **안정** |
| 삽입 정렬 (`>`) | 순서 유지 | 0 | 0 | 0 / 100 | **안정** |
| 삽입 정렬 (`>=`) | 순서 바뀜 | 5 | 9,900 (전부) | – | **불안정** |

### 5.4 선택 정렬 – 불안정

**실제 결과 (Test 1)**

```
입력       : (527, 100)#0 (527, 200)#1 (125, 300)#2 (892, 400)#3
선택 정렬  : (125, 300)#2 (527, 200)#1 (527, 100)#0 (892, 400)#3   ← 순서 바뀜
```

**원인**: 선택 정렬은 **멀리 떨어진 두 원소를 교환**합니다.

- i = 0: 최솟값 (125, 300)이 인덱스 2에 있으므로 a[0]과 a[2]를 교환합니다.
- 이때 a[0]에 있던 **(527, 100)이 (527, 200)을 건너뛰어** 인덱스 2로 가버립니다.
- 같은 키를 가진 원소를 사이에 두고 교환이 일어나면 상대적인 순서가 깨집니다.

Test 2에서도 맨 앞의 (3, 1)#0이 교환으로 뒤로 밀려나 (3, 6)#5 뒤에 놓였고(위반 1건),
Test 3에서는 9,900쌍 중 3,207쌍(약 32%)의 순서가 뒤집혔습니다.
무작위 데이터 100회 실험에서도 **100회 모두** 같은 키의 순서가 바뀐 경우가 발생했습니다.

### 5.5 버블 정렬 – 안정

**실제 결과 (Test 1)**

```
버블 정렬  : (125, 300)#2 (527, 100)#0 (527, 200)#1 (892, 400)#3   ← 순서 유지
```

**원인**

- 버블 정렬은 **인접한 두 원소끼리만** 교환하므로, 한 원소가 다른 원소를 "건너뛰는" 일이 없습니다.
- 교환 조건이 `a[j].key1 > a[j+1].key1` (**엄격한 부등호**)이므로, 같은 키를 가진 두 원소는 절대 교환되지 않습니다.
- 따라서 같은 키끼리는 서로 자리를 바꿀 기회가 없고, 처음 순서가 끝까지 유지됩니다.

Test 2, Test 3, 무작위 100회 모두 위반 0건이었으며, 조기 종료 버블 정렬도 교환 조건이 같으므로 동일하게 안정적이었습니다.
(참고: 교환 조건을 `>=`로 바꾸면 같은 키끼리 교환되어 불안정해집니다.)

### 5.6 삽입 정렬 – `>` 사용 시 안정

**실제 결과 (Test 1)**

```
삽입 정렬 (>)  : (125, 300)#2 (527, 100)#0 (527, 200)#1 (892, 400)#3   ← 순서 유지
```

**원인**: 새 원소(`current`)를 정렬된 구간에 삽입할 때, 앞쪽 원소가 `current`보다 **엄격하게 클 때만** 한 칸 뒤로 밉니다.
같은 키를 만나면 그 자리에서 멈추므로, 새 원소는 항상 **같은 키를 가진 기존 원소들의 뒤**에 놓입니다.
나중에 입력된 원소가 나중에 놓이므로 원래 순서가 유지됩니다. Test 2, Test 3, 무작위 100회 모두 위반 0건이었습니다.

### 5.7 삽입 정렬에서 `>`와 `>=`의 차이

```c
Case A : while (j >= 0 && a[j].key1 >  current.key1)   /* 같은 키에서 멈춤      */
Case B : while (j >= 0 && a[j].key1 >= current.key1)   /* 같은 키도 뒤로 밀어냄 */
```

**Test 1에서의 동작 추적** (i = 1, current = (527, 200)#1, a[0] = (527, 100)#0)

| | 비교 | 결과 | 배열 상태 |
|---|---|---|---|
| Case A (`>`) | 527 > 527 → 거짓 | 멈춤, current는 a[1]에 그대로 | (527,100)#0 (527,200)#1 → **순서 유지** |
| Case B (`>=`) | 527 >= 527 → 참 | (527,100)#0을 a[1]로 밀고 current를 a[0]에 삽입 | (527,200)#1 (527,100)#0 → **순서 뒤집힘** |

**실제 결과**

```
Test 1  Case B (>=) : (125, 300)#2 (527, 200)#1 (527, 100)#0 (892, 400)#3   ← 순서 바뀜

Test 2  입력       : (3,1)#0 (1,2)#1 (3,3)#2 (2,4)#3 (1,5)#4 (3,6)#5 (2,7)#6 (1,8)#7
        Case A (>) : (1,2)#1 (1,5)#4 (1,8)#7 (2,4)#3 (2,7)#6 (3,1)#0 (3,3)#2 (3,6)#5   위반 0
        Case B (>=): (1,8)#7 (1,5)#4 (1,2)#1 (2,7)#6 (2,4)#3 (3,6)#5 (3,3)#2 (3,1)#0   위반 5
```

Case B에서는 같은 키 그룹의 순서가 **정확히 거꾸로** 뒤집혔습니다 (예: Key1 = 1인 그룹이 #1, #4, #7 → #7, #4, #1).
새 원소가 같은 키를 가진 기존 원소들을 모두 지나 **그 앞**에 삽입되므로, 가장 나중에 들어온 원소가 항상 맨 앞에 오기 때문입니다.
Test 3에서도 같은 키 인접 쌍 **9,900쌍 전부**가 뒤집혀(위반 9,900건), 모든 그룹이 완전히 역순이 되었음을 확인했습니다.

**성능 차이 (Test 3 데이터)**

| | 비교 횟수 | 이동 횟수 |
|---|---:|---:|
| Case A (`>`) | 24,692,075 | 24,702,078 |
| Case B (`>=`) | 25,192,117 | 25,202,220 |
| 차이 | +500,042 | +500,142 |

Case B는 같은 키를 가진 원소까지 불필요하게 밀어내므로 비교와 이동이 각각 약 50만 회 더 발생했습니다.
키당 평균 100개가 있으면 같은 키 쌍은 100 × C(100, 2) ≈ 49.5만 개이고, 이 쌍마다 비교·이동이 1회씩 추가되므로 측정값과 일치합니다.

**결론**: Case B(`>=`)는 정렬 결과(오름차순) 자체는 올바르지만 **안정성이 깨지고 성능도 나빠집니다.**
삽입 정렬은 반드시 Case A(`>`)를 사용해야 안정 정렬이 됩니다. 프로그램의 성능 실험에서도 Case A를 사용했습니다.

### 5.8 안정성 판정의 핵심 원리

| 정렬 | 원소 이동 방식 | 같은 키끼리 위치가 바뀔 수 있는가? | 판정 |
|---|---|---|---|
| 선택 정렬 | 멀리 떨어진 원소와 교환 | 예 – 교환 시 같은 키를 건너뜀 | 불안정 |
| 버블 정렬 (`>`) | 인접 교환, 엄격한 부등호 | 아니오 | 안정 |
| 삽입 정렬 (`>`) | 한 칸씩 밀기, 같은 키에서 멈춤 | 아니오 | 안정 |
| 삽입 정렬 (`>=`) | 한 칸씩 밀기, 같은 키도 넘어감 | 예 – 같은 키 앞에 삽입됨 | 불안정 |

정리하면, 정렬의 안정성은 **(1) 원소가 같은 키를 가진 다른 원소를 건너뛰어 이동하는지**, **(2) 비교 연산자가 같은 키를 "이동해야 할 대상"으로 취급하는지** 에 따라 결정됩니다.
